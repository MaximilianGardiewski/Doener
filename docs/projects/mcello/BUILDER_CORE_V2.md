# Mcello — Builder Core V2

Stand: 2026-08-18

Status: **governed visual shell over the existing Mcello configurator**.

## 1. Purpose

Builder Core turns the already-existing modifier configurator into a food-first, step-based product-building experience without creating a second recipe, price, availability or cart model.

The existing application remains authoritative for:

- active product;
- `defaultSelected` standard recipe state;
- modifier rules and sold-out options;
- configuration validity;
- configured price;
- cart persistence;
- checkout/server/database validation.

## 2. Adobe concept pass

An Adobe Firefly concept pass was used only as a creative workshop for layout direction. Useful principles:

- large warm-neutral FoodStage;
- controls separated into visible steps;
- anthracite commerce chrome around the stage;
- copper as heat/material cue and olive as selective freshness/state cue;
- strong desktop split layout;
- mobile bottom-sheet behavior;
- persistent primary action at the bottom of the controls.

The generated concept is **CONCEPT ART ONLY**, is not a real Mcello product and is not a runtime media asset.

## 3. Mcello Original contract

D066 is implemented visually by reflecting the real configurator start state rather than inventing a recipe.

`app.js` initializes each modifier group from `option.defaultSelected` while excluding sold-out defaults. Builder Core snapshots the already-rendered checked inputs when the modal opens and labels that DOM state as the `Mcello Original` starting point.

If the user changes a modifier, Builder Core only changes the presentation label from `Standardauswahl` to `Angepasst`. It does not calculate or persist the selection itself.

## 4. FoodStage

The existing `#modalImage` becomes the Builder Core `FoodStage` surface.

Current phase:

- existing placeholder/CMS product media remains the only image source;
- no AI-generated ingredient is inserted as real Mcello food;
- Motion System V2 may provide visual selection feedback;
- no ingredient compositing is attempted yet.

Pizza and Döner/Yufka get their product-specific visual layer logic in later slices.

## 5. Step model

Existing `.modifier-group` sections are decorated as numbered Builder steps.

The number and content of steps come directly from the already-rendered modifier groups. Builder Core does not create, reorder or reinterpret modifier rules.

Every existing `.modifier-option` remains the actual radio/checkbox control generated by `app.js`.

## 6. Sticky action bar

The existing `.modal-footer` becomes the sticky Builder action bar.

The existing `#addToCart` button already displays the configured price from the existing application price function. Builder Core therefore does not duplicate price math; it only keeps that authoritative action visible while the modifier controls scroll.

## 7. Responsive contract

Desktop:

- two-column FoodStage + control stack;
- FoodStage remains visually stable while controls scroll;
- action bar remains visible at the bottom of the control pane.

Mobile:

- modal behaves like a bottom sheet;
- FoodStage uses the upper visual band;
- controls scroll below;
- action bar stays reachable;
- controls remain touch-first.

## 8. Accessibility and motion

- existing semantic inputs remain in the DOM;
- minimum touch targets reuse the V2 44/48px contracts;
- no drag interaction is required;
- reduced-motion behavior remains governed by Brand/Motion System V2;
- Builder Core adds no mandatory animation.

## 9. Product-specific handoff

### Pizza Builder

Uses this core with a top-down FoodStage and deterministic ingredient layers. The actual recipe and modifiers stay first-party/domain-owned.

### Döner/Yufka Builder

Uses the same core with a stable 3/4 assembly FoodStage and visible layer zones. It does not reuse Pizza's flat top-down metaphor.

No second configurator state model may be introduced by either product-specific slice.
