# Cloudflare Quick Tunnel edge mode

Status: implemented for **development/staging bootstrap and real-host E2E only**.

This mode exists so Supabase Factory can expose an isolated self-hosted project through Cloudflare without requiring a custom domain, DNS zone, Cloudflare account, Cloudflare API token, OAuth token, Wrangler session, or Cloudflare management MCP.

## Control path

```text
ChatGPT
  |
  v
Factory MCP
  |
  v
Supabase Factory
  |
  +-- Docker / isolated Supabase project
  |      |
  |      +-- Envoy 127.0.0.1:<project-port>
  |
  +-- cloudflared Quick Tunnel systemd unit
         |
         v
https://<random>.trycloudflare.com
```

Cloudflare is transport/edge only. Database, Auth, Storage configuration, migrations, secrets, backup, restore and lifecycle state remain owned by the self-hosted Factory.

## Factory implementation

`CloudflareQuickTunnelController`

- creates one Factory-owned systemd unit per project
- starts `cloudflared tunnel --no-autoupdate --url http://127.0.0.1:<envoy-port>`
- uses `DynamicUser=yes`
- gives cloudflared an isolated runtime `HOME`, avoiding interference from an operator's `~/.cloudflared/config.yaml`
- reads only the current systemd `InvocationID` from journald, so stale URLs from previous runs cannot be selected
- accepts only HTTPS TryCloudflare hostnames
- never accepts or persists Cloudflare API/OAuth/tunnel credentials
- never calls Cloudflare's management API
- never calls Caddy or requires wildcard DNS in this mode
- refuses to overwrite/remove non-Factory systemd units
- does not automatically restart a failed Quick Tunnel because a new cloudflared process receives a new random URL; URL churn must be surfaced through Factory state rather than hidden

`CloudflareQuickTunnelRuntimeBindingProvider`

- integrates with the existing `DockerComposeInfrastructureProvider`
- obtains the random public URL before Supabase runtime preparation
- passes that exact URL as both `publicUrl` and `siteUrl`
- therefore the existing runtime state and Supabase Auth/SITE_URL configuration use the real externally reachable URL
- refuses `production` projects and the `production-critical` profile

`CLOUDFLARE_QUICK_TUNNEL_PREFLIGHT_REQUIREMENTS`

- requires `cloudflared`
- requires `systemctl`
- requires `journalctl`
- does not require Caddy
- does not require wildcard-DNS resolver tooling
- leaves the normal migration/backup prerequisites unchanged

## Why no Cloudflare account is needed

Cloudflare documents Quick Tunnels / TryCloudflare as a zero-configuration development feature. Running:

```text
cloudflared tunnel --url http://localhost:8080
```

generates a random `trycloudflare.com` hostname and proxies it to localhost. A DNS zone or custom domain is not required.

Current upstream reference:

- https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/do-more-with-tunnels/trycloudflare/

## Known Cloudflare limitations

Quick Tunnels are explicitly intended by Cloudflare for testing/development, not production. Current documented constraints include:

- no SLA / uptime guarantee
- random hostname generated by the cloudflared process
- 200 concurrent in-flight request hard limit
- no Server-Sent Events (SSE)
- a normal `.cloudflared/config.yaml` can interfere with Quick Tunnel mode; Factory avoids this by using an isolated `HOME`

Because the URL belongs to the process lifecycle, a host reboot or an intentional new cloudflared process can produce a new URL. Factory therefore treats this mode as ephemeral and never silently promotes it to production.

## Production path remains independent

The existing stable edge providers remain available:

```text
CloudflareTunnelEdgeProvider
  -> one dedicated named tunnel
  -> one wildcard DNS record
  -> loopback Caddy host router
  -> isolated Envoy ports

ProjectEdgeBindingController
  -> direct Caddy HTTPS + wildcard DNS
  -> Cloudflare-independent fallback
```

Neither changes the core invariant: Supabase itself remains self-hosted and does not require Supabase Cloud management credentials.

## Real-host acceptance sequence

The next real-host E2E should prove:

1. Quick-Tunnel preflight succeeds on the target Ubuntu host.
2. Factory allocates a disposable development project.
3. Quick Tunnel starts and Factory captures the random HTTPS URL.
4. Supabase starts with that URL as its public/site URL.
5. Public Auth health succeeds.
6. REST with secret key succeeds.
7. REST without key returns 401.
8. Realtime WebSocket is tested explicitly.
9. Migration dry-run/apply is tested.
10. Encrypted off-host backup is created and verified.
11. Disposable restore drill succeeds.
12. Quick Tunnel unit and disposable project are cleaned up.

Production is not accepted through Quick Tunnel even if this E2E is green.
